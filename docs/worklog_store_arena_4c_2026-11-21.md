# 매장 경기장 RL 단계 4c: 노드 경로를 따라 다니는 다른 로봇과 함대 의도 관측 — 2026-11-21

4b(`docs/worklog_store_arena_4b_2026-11-21.md`: 사람·카트)의 경기장에 정해진 노드 경로로 다니는 로봇을 0~2대 넣었다. 관측에는 가까운 로봇 둘의 앞으로 갈 경로 점(함대 의도)을 더해 PPO로 처음부터 학습했다. 4c를 시작하기 전에 두 가지를 먼저 확인했다. 0a는 4b 정책을 Gazebo식(양보 없는) mover로 평가한 것이고, 0b는 mover 쓰기 비용을 잰 것이다.

**한 줄 결론:**

- **4c 학습:** 로봇·사람·카트·상자를 모두 넣은 환경에서 처음부터 학습한 정책(`ppo_h`, 600번 반복, 52분)은 결정적 평가 4096 에피소드에서 다음과 같았다.

  | 조건 | 성공 | 충돌 | 시간 초과 |
  |---|---|---|---|
  | 학습 때 본 배치 | 84.0 % | 6.0 % | 10.0 % |
  | 못 본 배치 | 84.4 % | | |

- **4b 정책과 비교:** 4b 정책(`ppo_g`)은 같은 환경에서 81.0 %였다. 로봇과의 충돌은 218건에서 85건으로 줄었다.
- **의도 지우기:** 의도를 0으로 지워도 전체 성공은 83.5 %로 0.5 %p만 떨어진다. 통계적으로 구별되지 않는다. 다만 결과는 바뀐다.
  - 시간 초과: 11.7 → 10.0 %로 준다.
  - 충돌: 4.7 → 6.0 %로 는다.
  - 로봇과 0.10~0.25 m까지 간 에피소드의 성공: 76.9 → 84.4 %.

  정책이 의도를 쓰기는 하지만, 쓴 만큼 이득이 나지는 않았다.
- **남은 실패:** 대부분 좁은 남쪽 통로에서 로봇과 마주 선 경우다. 로봇이 3 s 기다렸다 2 s 물러나고 다시 오는 사이에 우리 로봇이 지나가지 못한다(`d_eval_env6_timeout.gif`).
- **4b 시험 세트:** 로봇이 없는 4b 시험 세트에서는 92.9 %로, 4b 정책의 93.6 %보다 0.7 %p 낮다.
  - 충돌: 4.0 → 3.1 %
  - 시간 초과: 2.4 → 4.0 %

## 0. 4c 전 확인 두 가지

### 0a. 4b 정책을 Gazebo식 mover로 (`c_eval_499_noyield.json`)

`--set mover_yield_m=0`이면 mover가 기다리지 않는다. 기다림이 없으니 돌아서기(`wait_s` 뒤)도 일어나지 않는다. Gazebo 비교 묶음의 mover와 같은 동작이다. 같은 seed·배치로 4096 에피소드를 돌렸다.

| mover와 가장 가까웠던 거리 | 양보함(B21~B23, `c_eval_499`) | 양보 없음 |
|---|---|---|
| 전체 | 성공 94.6 %, 충돌 3.0 %, 시간 초과 2.4 % | **87.5 %, 10.5 %, 2.0 %** |
| mover 없음 | 96.0 % | 95.2 % |
| 0.10 m 미만 | 90.5 % (충돌 53) | **59.3 % (충돌 365)** |
| 0.10~0.25 m | 95.9 % | 96.4 % |
| 0.25~0.50 m | 95.3 % | 96.5 % |
| 0.50 m 이상 | 94.6 % | 94.0 % |

틈은 7.1 %p이고 거의 모두 0.10 m 안까지 온 에피소드의 충돌이다. mover가 로봇에게 걸어 들어오면 정책은 피하지 못한다. B21의 양보가 학습만 쉽게 한 것이 아니라 평가 숫자도 그만큼 좋게 만든다. Gazebo와 견줄 때는 양보 없는 숫자(87.5 %)를 써야 한다.

### 0b. mover 쓰기 비용 (`c_prof_movers.json`, 측정 스크립트 `c_prof_movers.py`)

4096 env, `env.step` 60번의 평균을 다섯 가지 방법으로 쟀다. 결과는 B41에 있다.

| 방법 | ms/스텝 | 시뮬과 mover_state 차 |
|---|---|---|
| A 지금(자세 + 속도 0 쓰기) | 106.7 | 5 µm |
| B 쓰기 없음(mover 서 있음) | 117.6 | (움직이지 않으니 2.2 m) |
| C 자세만 | 107.0 | 5 µm |
| D 자세만 + `skip_forward` | 101.8 | 5 µm |
| E notify 끔 | 108.4 | 5 µm |

- `is_floating_base`가 참이라 Newton이 `notify_model_changed`를 부르지 않는다. 의심했던 경로는 처음부터 타지 않았다.
- 쓰기를 아예 빼도 빨라지지 않는다. B는 측정 잡음이다.
- **결론: 고칠 곳이 쓰기에는 없다.** 4a 1.1 s → 4b 2.6 s의 차이는 다른 데서 온다. mover 강체가 장면에 있는 것 자체(충돌 검사·라이다 광선)일 수도 있고, 스텝마다 도는 torch 계산일 수도 있다.
- 4c는 강체가 env마다 2개 더 늘어 반복당 5.1 s다.
- 어느 쪽인지 가르려면 "강체는 있고 계산은 없는" 변형과 "강체 없이 계산만" 변형을 재야 한다(남은 것).

## 4. 학습 `ppo_h` (`d_train_curves.png`, `d_train_metrics.csv`, `d_train_run.json`)

```
bash learning/store_arena/run_train.sh /d/isaac/runs/store_arena/ppo_h 2 300 4096 --set robot_max=2 --set intent_robots=2
chunk 1 exit=0 wall_total_s=1594
chunk 2 exit=0 wall_total_s=1574
```

- 정책 입력: `Linear(in_features=55, ...)`
- 학습 시간: 1566 + 1545 s. 반복당 5.1 s(4b는 2.6 s)
- 메모리: GPU 최대 5108 MiB, CUDA 최대 할당 691 MB
- 성공률이 처음 넘은 시각:

  | 성공률 | 50 % | 70 % | 80 % | 85 % |
  |---|---|---|---|---|
  | 시각 | 134 s | 257 s | 578 s | 885 s |

- 마지막 100번 반복 평균:

  | 성공 | 충돌 | 시간 초과 | 성공 시간 |
  |---|---|---|---|
  | 84.7 % | 6.3 % | 9.0 % | 7.55 s |

- 두 번째 덩어리는 거의 늘지 않았다(84.5 → 85.2 %).
- 26분 근처의 튀는 점은 덩어리를 이어 받은 직후 통계가 빈 반복이다. 학습 자체가 튄 것이 아니다.

## 6. FollowPathRL 플러그인의 `policy_spec.json`이 알아야 할 것

`task_spec.obs_names(spec)`가 이름과 순서를 준다. 내보낼 때 아래 값을 함께 적어야 한다.

- **이름과 순서:** `lidar_sector_0..35`, `goal_dist`, `goal_sin`, `goal_cos`, `v`, `w`, 그리고 `r = 0..intent_robots-1`마다 다음 7개.
  - `robot{r}_present`
  - `robot{r}_p1_x`, `robot{r}_p1_y`
  - `robot{r}_p2_x`, `robot{r}_p2_y`
  - `robot{r}_p3_x`, `robot{r}_p3_y`

  4c 정책은 55차원이다.
- **설정값:** `intent_robots` 2, `intent_points` 3, `intent_spacing_m` 0.2, `intent_obs_max` 2.0.
- **좌표계:** 우리 로봇 base_link, x 앞, y 왼쪽, m. 라이다 중심(0.017 m 뒤)이 아니다.
- **배율:** `/ intent_obs_max` 다음 [-1, 1]로 자른다.
- **순서 규칙:** 우리 로봇 중심과 그 로봇 중심의 거리가 가까운 순. 매 제어 주기(20 Hz)마다 다시 정한다.
- **점 계산:** 그 로봇의 현재 경로(노드 목록을 직선으로 이은 것)를 따라 지금 위치에서 0.2·0.4·0.6 m 앞이다. 경로 목표를 넘지 않고 넘으면 목표에 붙인다. 쉬는 중이거나 경로가 없으면 세 점 모두 그 로봇 위치다(시뮬에서는 쉬는 목표 위치).
- **채움:** 로봇이 `intent_robots`보다 적으면 남는 칸 7개를 모두 0(`present` 0).
- **필요한 입력:** fleet_manager가 다른 로봇마다 현재 경로의 남은 점과 자세를 우리 로봇에게 줘야 한다. 우리 로봇의 자세도 같은 지도 좌표계로 필요하다.
- **차이:** 시뮬은 로봇 위치를 정확히 안다. 실제는 지연과 위치 추정 오차가 있다. 평가에 넣지 않았다(남은 것).

## 9. 배운 것

- **양보 없는 mover:** 4b 숫자의 7 %p가 mover의 양보 덕이었다. 정책이 피해서가 아니다. 시뮬 쪽 행동 규칙을 바꾸면 그 규칙의 몫을 꼭 따로 재 두어야 한다.
- **의도 관측:** 의도를 넣어도 전체 성공이 오르지 않았다. 지워 보면 결과가 시간 초과 ↔ 충돌로 옮겨 간다. "쓰는가"와 "득이 되는가"는 다른 질문이고, ablation이 둘을 갈라 준다.
- **남은 실패의 원인:** 정책보다 스크립트 로봇의 교착 규칙에서 온다. 상대가 좁은 통로에서 계속 되돌아오면 어떤 정책도 통과 못 할 수 있다. 실제 fleet_manager는 레인 잠금으로 이런 마주침을 줄이니, 시뮬의 상대 행동을 그쪽에 가깝게 하는 것이 다음 할 일이다.
- **속도 병목:** 쓰기 API를 의심했지만 재 보니 아니었다. 고치기 전에 재는 것이 맞았다. 다만 진짜 병목은 아직 모른다.

## 10. 알아야 할 포인트

### 10.1 쓰인 개념

- **함대 의도(fleet intent):** 관제가 아는 다른 로봇의 앞으로 갈 길. 라이다는 지금만 보지만, 의도는 몇 초 뒤를 알려 준다.
- **운동학(kinematic) 강체:** 물리 계산으로 움직이지 않고 매 스텝 자세를 써서 옮기는 물체. 다른 물체를 밀어내지만 밀리지 않는다.
- **최단 경로(Floyd-Warshall):** 노드 7개의 모든 쌍 최단 경로를 한 번에 구한다.
- **ablation:** 입력 하나를 지우고 성능을 다시 재서, 모델이 그 입력을 쓰는지 본다.
- **표준오차:** 성공률 p, 에피소드 n이면 √(p(1-p)/n). 4096 에피소드, 85 %면 약 0.56 %p.

### 10.2 먼저 볼 곳 (3개)

1. `learning/store_arena/robot_spec.py`의 `chain_route`, `robot_step`, `intent_points`: 로봇이 어떻게 움직이고 무엇이 관측되는가.
2. `learning/goal_reach/task_spec.py`의 `obs_dim`, `obs_names`, `build_observation`: 관측 배치의 한 정의.
3. `learning/store_arena/store_arena_env.py`의 `robot_intent`, `_sample_robots`: 가까운 순 정렬과 금지 노드.

### 10.3 결과 숫자 읽는 법

- `by_robot_gap`은 결과에 따라 바뀌는 거리로 나눈 것이다. 정책끼리 구간 수가 다르면 구간 성공률을 바로 비교하지 않는다.
- 전체 비율과 표준오차를 먼저 본다.
- `collisions_by_nearest`는 추정이다(B40).

### 10.4 스스로 확인할 질문

- 의도 점이 다음 경로로 넘어가지 않게 한 이유는? (B35)
- `robot_max` 기본이 0인 이유와, 0일 때 난수를 뽑지 않아야 하는 이유는? (B38)
- 4b 정책이 4c 환경에서 로봇과 218번 부딪히는데 왜 성공은 81 %나 되나? (로봇 없는 에피소드 1/3, 로봇이 0.25 m에서 섬)

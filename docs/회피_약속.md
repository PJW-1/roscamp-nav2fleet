# 회피 쪽 기준 (사용자 기준)

이 문서는 사용자 기준이며, 회피 담당은 이 기준에 맞춥니다(추가 지시서 3의 7절). 넓은 구역에서 장애물과 다른 핑키를 피하는 일은 로봇의 Nav2가 맡고, 관제는 어느 구역에 들어가도 되는지만 정합니다. 값은 Gazebo에서만 쟀고 실물에서는 재지 않았습니다.

## 1. 맡는 범위

| 항목 | 기준 |
|---|---|
| 회피 담당이 맡는 것 | 넓은 구역의 Nav2 goal을 모는 컨트롤러 `FollowPathGoal` 안의 값, costmap 장애물 층의 비전 관측원 값, 비전 장애물을 내는 노드 |
| 사용자가 맡는 것 | 그 밖의 Nav2 설정 모두(2절의 표), 고정 경로 주행(`FollowPath`, `FollowPathThrough`, `FollowPathReverse`), keepout, 벽 근처 scan 거르기(3절), 로봇단 교착 처리(5절), 관제 |
| 회피 범위 | 관제가 잡아 준 구역 안에서만 피합니다. keepout 구역(급행, 도크, 갈림목)에는 들어가지 않습니다 |
| 고정 경로 위 | 피하지 않습니다. 막히면 서고 `BLOCKED`를 보고합니다. 그다음은 관제가 정합니다(`관제_구역교통.md` 규칙 7) |
| 다른 핑키 | costmap에 보이는 다른 핑키도 장애물로 피합니다. 마주 서서 못 가면 로봇단 교착 처리(5절)가 먼저 움직이고, 그래도 안 되어 `BLOCKED`가 온 뒤에 관제가 움직입니다(`관제_구역교통.md` 규칙 6, 7, 7a) |
| 잠깐 지나가는 사람 | 8초쯤 막혔다 풀리면 관제는 아무것도 하지 않습니다. 우회도 후진도 없습니다 |

## 2. 설정의 주인

| 설정 | 주인 | 회피 담당이 바꾸려면 |
|---|---|---|
| 발자국, local·global costmap 크기와 칸, inflation, keepout | 사용자 | 사용자에게 요청 |
| 장애물 층의 라이다 관측원, scan 거르기 | 사용자 | 사용자에게 요청 |
| progress checker, goal checker, `blocked_after_s` | 사용자 | 사용자에게 요청 |
| bt_navigator, BT XML, planner, FollowPath 셋 | 사용자 | 사용자에게 요청 |
| `FollowPathGoal` 컨트롤러 안의 값 | 회피 담당 | 4절 기준 안에서 자유 |
| 장애물 층의 비전 관측원(`/<robot>/vision_obstacles`) 값 | 회피 담당 | 4절 기준 안에서 자유 |
| 다른 로봇의 몸을 찍는 peer 층(`params/peer_obstacles.yaml`, `pinky_peer_obstacles`) | 사용자가 임시로 만듦(2026-11-13, 주행 시험용). 회피 담당의 영역 | 회피 담당이 자기 방식으로 바꿔도 됩니다(9절) |

설정 파일은 둘입니다(`pinky/pinky_nav_config/params/`).

| 파일 | 주인 | 내용 |
|---|---|---|
| `nav2_params.yaml` | 사용자 | Nav2 파라미터 파일 그대로입니다. `FollowPathGoal`의 값과 비전 관측원의 값은 없고, 컨트롤러 이름 `FollowPathGoal`만 `controller_plugins`에 있습니다 |
| `avoidance.yaml` | 회피 담당 | 키가 둘뿐입니다. `follow_path_goal`은 `controller_server`의 `FollowPathGoal` 안에 그대로 들어가고, `vision_obstacles`는 launch 인자 `vision_obstacles:=true`일 때 두 costmap 장애물 층의 `vision` 관측원 안에 그대로 들어갑니다 |

- 회피 담당 파일에 다른 키가 있으면 `nav2.launch.py`가 뜨지 않고(`ValueError`), `test/test_nav_config.py`의 `test_a_user_owned_key_in_the_avoidance_file_is_refused`와 `test_the_avoidance_file_holds_only_the_two_avoidance_keys`가 실패합니다.
- 사용자 파일에 회피 담당의 값이 들어 있어도 시험이 실패합니다(`test_the_users_file_holds_no_avoidance_values`). 값의 자리는 하나입니다.
- 두 파일을 모으는 함수는 `launch/pinky_nav_params.py`의 `with_avoidance`입니다(ROS 없이 돕니다).
- 시뮬레이션은 회피 담당 파일의 `FollowPathGoal`에 속도 상한(`nav_max_speed`)과 충돌 검사 켬을 덮어서 씁니다(`sim_nav_params`). 이 두 값은 RPP의 키입니다. `FollowPathGoal`을 RPP가 아닌 플러그인으로 바꾸면 시뮬레이션이 속도 상한을 넣어 주지 못하므로, 회피 담당 파일이 스스로 `nav_max_speed`를 지켜야 합니다.

## 3. 벽 근처 scan 거르기 (사용자의 것)

폭 0.20 m인 좁은 띠에서는 라이다 잡음이 벽을 몸 발자국 안에 찍어서 고정 경로의 충돌 검사가 로봇을 세웠습니다. 그래서 좁은 띠 안에서만 벽에 붙은 점을 costmap에서 지웁니다(`pinky/pinky_scan_filter`, 추가 지시서 3의 7-2).

| 항목 | 내용 |
|---|---|
| 지우는 점 | 좁은 띠(급행, 갈림목, 도크) 안에 있고, 1 cm 지도(`map_fine`)의 벽·진열대에서 `wall_band_m` 안에 있는 라이다 점입니다. 넓은 구역의 점은 그대로 둡니다 |
| 띠에 더한 곳 둘 | ① 진열대 끝면마다 끝면을 `wall_band_m`만큼 사방으로 넓힌 작은 상자(D2에서는 `0.45,0.725,0.55,0.84`와 `1.43,0.725,1.53,0.84`). 끝면의 잡음이 띠 바로 밖에 떨어져 후진 모퉁이를 막았기 때문입니다. ② 경기장 벽에 닿은 띠의 변은 `wall_band_m`만큼 벽 너머로 넓혔습니다. 잡음과 위치 추정 오차로 벽 면 너머에 찍힌 점이 띠 밖이라 지워지지 않았기 때문입니다 |
| 값 | `wall_band_m` 0.05 m입니다. 지시서의 제안값은 0.04 m였지만 Gazebo(D2, 잡음 0.02)에서 0.04 m는 도크 진입이 두 번 가운데 한 번만 성공했고 0.05 m는 세 번 모두 성공했습니다(`sim/fleet_gz_sim/results/fixed_line_results.md`). 점을 AMCL 자세로 지도에 놓기 때문에, 띠 폭이 라이다 잡음과 위치 추정 오차를 함께 덮어야 합니다 |
| 누가 읽나 | 두 costmap의 장애물 층은 거른 `scan_filtered`를 읽고, AMCL은 원래 `scan`을 읽습니다 |
| 켜는 법 | `nav2.launch.py`의 인자 `narrow_strips`(좁은 띠 사각형들, map 좌표)를 주면 노드가 뜨고 `params/scan_filter.yaml`이 얹힙니다. 비어 있으면(기본) 노드도 덧붙임도 없습니다 |
| 대가 | 좁은 띠 안에서 벽에 붙어 있고 `wall_band_m`보다 얇은 물체는 보이지 않습니다. 띠 안의 벽에서 0.05 m 안에 놓인 물체가 그 예입니다. 진열대 끝 둘레 0.05 m 안(마당 쪽 진열대 면의 끝 0.05 m 조각 포함)에 놓인 얇은 물체도 보이지 않습니다. 지도는 1 cm 격자여서 경계에 몇 mm의 오차가 있습니다 |
| 어느 때의 자세로 거르나 | 스캔을 찍은 시각의 TF를 0.05 s까지 기다려 씁니다. 그 시각의 TF가 없으면 최신 TF를 쓰되, 스캔 시각과 0.1 s 넘게 차이 나면 거르지 않습니다. TF는 거르개와 따로 도는 도우미 노드(`scan_filter_tf`)가 받습니다 |
| 거른 빔으로 칸 지우기 | 거르개가 지운 빔은 `inf`입니다. 거르개를 켠 설정(`scan_filter.yaml`)에서만 두 costmap의 `obstacle_layer.scan`에 `inf_is_valid: true`를 두어, 그 빔을 따라 칸을 지웁니다(`raytrace_max_range` 3 m까지, 찍지는 않습니다). 꺼져 있을 때는 띠 안에 한 번 찍힌 칸(잡음, 지나간 다른 로봇의 몸)이 남아 고정 경로의 `collision ahead`로 이어졌습니다: Gazebo 한 대 세 바퀴에서 고정 경로 구간의 자가 복구가 8~12번이었고 켠 뒤 0번입니다 |
| 그 대가와 조건 | 거른 빔이 지나는 길 위(벽 띠 안)에 서 있는 진짜 장애물이나 다른 로봇의 칸, 벽·진열대 너머에 가려진 장애물의 칸도 지워질 수 있습니다. 다음 스캔에 보이는 것은 다시 찍힙니다. 라이다의 `range_max`가 `raytrace_max_range`(3.0 m)보다 커야 합니다(시뮬레이션 12 m. 실물 sllidar의 값은 확인하지 않았습니다. 2.5 m보다 짧으면 지운 빔의 끝이 가짜 장애물로 찍힙니다) |
| 회피에 주는 영향 | 작습니다. `FollowPathGoal`은 keepout 때문에 좁은 띠로 들어가지 않고, 넓은 구역의 점은 거르지 않습니다 |
| 안전한 쪽 | 지도나 TF를 받지 못할 때, TF가 낡았을 때, 스캔에 시각이 없을 때(stamp 0), 지도의 원점이 돌아가 있을 때는 거르지 않은 scan을 그대로 냅니다. 이때는 로봇이 덜 서는 것이 아니라 더 자주 섭니다 |

## 4. 회피가 지켜야 할 기준

회피 담당의 변경은 이 표를 지키고 회귀 시험을 통과해야 들어옵니다.

| 기준 | 값 |
|---|---|
| 컨트롤러 이름 | `FollowPathGoal` 고정. 안의 플러그인(RPP, MPPI, DWB)과 값은 회피 담당이 정합니다 |
| 속도 상한 | `nav_max_speed`를 따릅니다(Gazebo launch 인자, 0.12~0.20 m/s, 기본 0.12). 컨트롤러가 그보다 빠른 속도를 내면 안 됩니다 |
| keepout 침범 | Gazebo 세 대 경기에서 몸이 keepout 구역으로 들어간 깊이가 `keepout_intrusion_max_m`(0.02 m) 이하입니다. 재는 법은 아래에 있습니다 |
| 막히면 | `blocked_after_s`(10초) 안에 서고 `BLOCKED`를 보고합니다. 헛돌면서 `MOVING`으로 남으면 안 됩니다 |
| `obstacle_kind` | 비전이 채웁니다. 값은 `unknown` / `person` / `object` / `robot`. 비전이 없는 지금은 `unknown`만 씁니다 |
| 회귀 시험 | 주행 완료 기준(작업 기록의 2-5 표)과 매장 상황 시험(`막힘_처리_결과.md`)을 통과해야 합니다. 한 명령으로 돌립니다(아래) |

비전 입력의 기준입니다. 받는 쪽(costmap 장애물 층)은 사용자가 띄우고, 보내는 쪽은 회피 담당이 만듭니다.

| 항목 | 기준 |
|---|---|
| 토픽 이름 | `/<robot>/vision_obstacles` (로봇 namespace 안의 `vision_obstacles`) |
| 타입 | `sensor_msgs/PointCloud2`. 필드 `x`, `y`, `z`(float32). 장애물인 점만 보냅니다(바닥 점은 보내는 쪽에서 뺍니다) |
| QoS | 장애물 층은 sensor data QoS(best effort, keep last)로 받습니다. 보내는 쪽은 best effort나 reliable 어느 쪽이든 닿습니다 |
| `frame_id`와 TF | `header.frame_id`는 로봇의 TF(`/<robot>/tf`, `/<robot>/tf_static`)에 있는 프레임이어야 합니다(카메라 프레임이나 `base_footprint`). 장애물 층이 `odom`(local)과 `map`(global)으로 옮깁니다. 프레임 이름에 로봇 이름 접두사를 붙이지 않습니다 |
| `header.stamp` | 사진을 찍은 시각입니다(시뮬레이션에서는 sim time). 그 시각의 TF가 있어야 점이 쓰입니다. 처리에 걸린 시간만큼 늦은 시각을 그대로 적습니다(지금 시각으로 바꿔 적지 않습니다) |
| 주기 | 5 Hz 이상을 권합니다(local costmap이 5 Hz로 갱신합니다). 토픽이 조용해도 costmap은 멈추지 않습니다(`expected_update_rate` 0) |
| 높이 범위 | `min_obstacle_height` 0.0 m ~ `max_obstacle_height` 2.0 m 안의 점만 씁니다(로봇 바닥 기준). 범위 값은 회피 담당의 것입니다 |
| 지워지는 때 | 표시만 합니다(`marking`). 찍힌 칸은 라이다 광선이 그 칸을 지나갈 때만 지워집니다. 라이다보다 낮은 물체의 표시는 costmap을 비울 때까지 남습니다. 언제 지울지는 회피 담당이 정합니다 |

### 회귀 시험 명령

```bash
source /opt/ros/jazzy/setup.bash && source install/setup.bash    # colcon build 한 뒤
export ROS_DOMAIN_ID=45 ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST   # 6은 쓰지 않는다
tools/avoid_regression.sh                # 결과는 avoid_regression_out/, 통과면 0으로 끝난다
```

| 단계 | 무엇을 돌리나 | 통과 조건 |
|---|---|---|
| 1 | 머리 없는 세계의 매장 상황(`tools/situations.py --store --avoid all`, 흉내 세 모드 × 씨드 셋) | 못 지킨 기대가 없습니다 |
| 2 | Gazebo 한 대(D2), 구간 종류마다 세 번(`drive_check`). 고정 경로의 충돌 검사는 기본이 끔이고(사용자 결정 2026-11-13), `--fixed-line-check true`로 켜고 돌릴 수 있습니다 | 모든 이동이 성공하고, Nav2 계획과 로봇 중심이 keepout 구역에 들어가지 않습니다 |
| 3 | Gazebo 세 대 경기 세 판(씨드 1, 2, 3) | 끝나지 않은 주문의 원인(`tools/triage`)에 "주행"이 없고, keepout 침범 깊이가 0.02 m 이하입니다 |

- 판정은 `tools/avoid_regression.py`가 합니다(ROS 없이 돕니다). 한 단계가 실패해도 나머지 단계를 돌리고, 하나라도 실패하면 1로 끝납니다.
- 인자: `--out <폴더>`, `--games <판 수>`, `--laps <횟수>`, `--seeds "1 2 3"`, `--keepout-max <m>`, `--skip-headless`, `--skip-gazebo`.
- keepout 침범 깊이는 `fleet_check`가 Gazebo의 실제 자세와 Nav2 발자국(`nav2_params.yaml`의 `footprint`)으로 잽니다(`fleet_check.json`의 `keepout_depth_m`). 로봇 중심이 넓은 구역에 있을 때, 발자국 둘레의 점(0.5 cm 간격)이 그 로봇이 쥐지 않은 좁은 구역 안으로 들어간 깊이(구역 사각형의 가장 가까운 변까지)입니다. 로봇이 쥐고 있거나 5초 안에 쥐었던 구역은 세지 않습니다(그 구역에서 나오는 중인 몸의 꼬리입니다). 한 번도 재지 못한 경기(자세나 구역 메시지가 오지 않음)와 끝까지 돌지 못한 경기(`summary.json` 없음, 시간 한도)는 통과로 치지 않습니다.
- 끝나지 않은 주문의 원인이 "회피"인 경우는 표에 찍히지만 지금은 실패로 치지 않습니다(지시서의 주행 완료 기준이 "주행" 원인 0건입니다). 이것도 실패로 칠지는 사용자가 정합니다.
- 지금 시작값(RPP)이 0.02 m를 지키는지는 이 새 측정으로 다시 재야 합니다. 예전 측정(7.2절: 0.12 m 사각형 몸, 쥔 구역을 빼지 않음)에서는 가장 깊게 0.04~0.05 m였습니다. 기준을 넘으면 keepout을 넓히는 방법(`tools/make_keepout.py --pad 0.085`)과 기준값을 다시 정하는 방법 가운데 사용자가 고릅니다.

## 5. 로봇단 교착 처리 (사용자의 것)

로봇이 막혔을 때 기다리고, 물러나고, `BLOCKED`를 보고하는 순서는 `pinky_fsm`이 정합니다(추가 지시서 3의 7-4, 계약 0.13-draft). 회피 담당은 이 순서를 바꾸지 않습니다.

| 항목 | 내용 |
|---|---|
| 누가 정하나 | `pinky_fsm` 하나입니다. 고정 경로(`follow_path`)와 넓은 구역(`nav_goal`) 두 모드 모두에서 기다림, 물러나기, `BLOCKED`를 정합니다. Nav2의 행동 트리는 지도 지우기와 Wait만 합니다: Spin과 BackUp을 트리에서 뺐고 `behavior_plugins`에서도 `spin`을 뺐습니다 |
| 순서 | 물체 앞에 1초 서면 `RECOVERING`(`local_yield=wait`)으로 `local_wait_s`(2초) 기다립니다 → 앞을 막은 것이 다른 로봇이고 내가 낮은 쪽이면 물러납니다(`backup`) → 다시 갑니다(`retry`) → 또 막히면 `BLOCKED`입니다. 물러나지 않는 쪽은 기다린 뒤 바로 `BLOCKED`입니다. 한 자리에서 한 번만 합니다 |
| 누가 물러나나 | `(priority, 로봇 이름)`이 작은 쪽입니다. 관제가 MoveTo의 `priority` 칸으로 주고, 둘 중 하나라도 값이 없거나(-1) 같으면 이름 순입니다. 앞을 막은 로봇은 `/fleet/robots`의 위치로 찾습니다. 비전의 `obstacle_kind=robot`은 어느 로봇인지 알려 주지 않아서 쓰지 않습니다 |
| 물러나는 거리 | `local_backup_m`(0.10 m)과 지금 goal에서 지나온 거리 가운데 작은 값입니다. goal을 막 시작해서 지나온 거리가 없으면 물러나지 않습니다 |
| `blocked_after_s` | 10초입니다. 선 때부터 `BLOCKED`까지의 상한이고, 위의 순서를 다 하고도 3초쯤 남습니다 |
| 관제와의 순서 | 로봇단 처리가 먼저입니다. 관제는 그동안 사건 `LOCAL_YIELD`로 남기기만 하고, `HALL_YIELD`와 규칙 7은 `BLOCKED` 뒤에 움직입니다 |
| 회피 담당이 지킬 것 | `FollowPathGoal`이 스스로 후진하거나 제자리에서 오래 돌아서 이 순서와 겹치지 않게 합니다. 못 가면 서 있으면 되고, 그다음은 `pinky_fsm`이 합니다 |
| 끄는 법 | `pinky_fsm` 파라미터 `local_yield`(기본 켬) |
| 아직 Gazebo에서 보지 않은 것 | 고정 경로와 넓은 구역에서 마주 선 두 대, `BLOCKED`가 10초 안에 나오는지, 트리가 `pinky_fsm` 모르게 로봇을 움직이지 않는지 |

### 7.3 Nav2 복구 동작 (2026-11-12, 트리에서 Spin과 BackUp을 빼기 전)

그때의 행동 트리는 goal이 막히면 Spin, Wait, BackUp을 차례로 해 봤습니다. 아래 결과를 근거로 Spin과 BackUp을 트리에서 뺐습니다(5절). 탐침 표는 `sim/fleet_gz_sim/results/backup_spin_probe.md`에 있습니다.

| 확인 | 어디서 몇 번 | 결과 |
|---|---|---|
| 세 대 경기에서 복구가 실패한 횟수 | Gazebo, 세 대 경기 로그 19개(경기마다 한 판) | Spin 실패 101번, BackUp 실패 50번입니다. 모두 "Collision Ahead"로 끝났습니다. 성공한 횟수는 모릅니다: 경기 로그는 경고부터만 남겨서 성공은 적히지 않습니다 |
| 정면에 진열대나 서 있는 핑키가 있을 때 Spin | Gazebo, 핑키 한 대, 몸 틈 0.10~0.015 m에서 10번 | 10번 모두 실패했습니다(오류 703). 0.07~0.22 rad 돌다가 멈춥니다. 빈 곳(둘레 0.32 m)에서는 2번 모두 성공했습니다. 실패가 시작되는 틈은 0.10 m와 0.32 m 사이이고 더 좁히지 않았습니다 |

### 7.4 관제가 시키는 물러나기 (제안, 기본 꺼짐)

로봇단 교착 처리(5절)가 먼저이고, 이것은 `BLOCKED`가 온 뒤에 관제가 보내는 것입니다.

| 항목 | 내용 |
|---|---|
| 언제 | 넓은 구역에서 두 대가 가까이 서서 못 나아가고(규칙 6), 비킬 로봇이 BLOCKED를 보고했을 때입니다. BLOCKED 보고가 없으면 `yard_backoff_wait_s`(0.5초)를 더 기다렸다가 그냥 세웁니다 |
| 무엇을 | `retreat`에 곧은 경로(지금 자리에서 뒤로 `yard_backoff_m` 0.12 m)를 넣어 보냅니다. 핑키는 `FollowPathReverse`로 0.05 m/s로 따릅니다. 끝나면 5초 서 있다가 원래 목적지를 다시 받습니다 |
| 내지 않는 때 | 뒤로 가는 선이 로봇이 쥔 넓은 구역을 벗어나거나, 진열대를 지나거나, 끝 자리가 벽·진열대·고정 구간에서 0.10 m 안이거나, 뒤쪽 0.20 m 안에 다른 로봇이 있거나, 끝 자리가 그 로봇이 쥐지 않은 지점에서 0.20 m(`node_clear_m`) 안일 때입니다. 그때는 그 자리에 세웁니다 |
| 실패하면 | 시도 횟수로 세지 않고 그 자리에 세웁니다(`HALL_BACKOFF_FAILED`) |
| 켜는 법 | 관제 파라미터 `yard_backoff`(기본 꺼짐). Gazebo 세 대 경기로는 아직 재지 않았습니다(머리 없는 세계에서만 시험했습니다) |

## 8. 회피 담당과 정할 것

기준으로 정하지 않고 남겨 둔 것입니다.

| 물음 | 까닭 |
|---|---|
| keepout을 얼마나 넓힐까요(지금 0.06 m) | 0.06 m는 곧게 선 몸의 반폭입니다. 45도로 선 몸의 모서리는 0.085 m까지 나가서 구역에 0.025 m 걸칠 수 있습니다. `tools/make_keepout.py --pad 0.085`로 바꿀 수 있고, 그만큼 마당이 좁아집니다. 4절의 keepout 침범 기준을 새로 잰 뒤에 정합니다 |
| 비전 장애물 표시를 언제 지울까요 | 지금 자리는 표시만 합니다. 찍힌 칸은 라이다 광선이 지나갈 때만 지워지고, 시간으로는 지워지지 않습니다 |
| 다른 핑키의 몸을 costmap에 어떻게 넣을까요 | Gazebo에서 라이다는 다른 핑키의 라이다 머리만 봅니다(7.2절). 세 대 경기 열 판 가운데 다섯 판에서 몸이 닿았습니다. 실물 핑키도 몸이 라이다 빔보다 낮으면 같습니다. 관제가 다른 로봇의 위치를 장애물로 내주는 방법도 있습니다 |
| `obstacle_kind`를 비전이 어떻게 넘길까요 | 값의 종류는 정했지만(4절), 비전 노드가 `pinky_fsm`에 넘기는 길은 비전이 들어올 때 정합니다 |

비전이 들어온 뒤에 다시 맞출 값: 관제의 `blocked_mark_s`, 사람으로 보고 기다리는 시간, `obstacle_kind`별 처리, 규칙 6의 거리와 시간(`near_m`, `near_stuck_s`).

## 9. 임시: 다른 로봇의 몸을 costmap에 (peer 층, 2026-11-13)

회피 담당의 영역이지만 사용자가 주행 시험을 하려고 임시로 만들었습니다. 회피 담당이 자기 방식(비전, 다른 층)으로 바꿔도 됩니다.

기본값은 둘로 나뉩니다. Gazebo(`gz.launch.py`)는 **켜짐**입니다(사용자 결정 2026-11-13, 근거는 작업 기록 11절). 로봇의 `nav2.launch.py`는 **꺼짐** 그대로입니다: 실물에서 재지 않았고, 켜려면 로봇 이름 목록(`peer_robots`)을 줘야 합니다. 꺼져 있으면 아무것도 바뀌지 않습니다.

| 무엇 | 내용 |
|---|---|
| 왜 | 라이다 빔이 다른 핑키의 몸 위로 지나가 costmap에 작은 점으로만 찍힙니다. Nav2가 다른 로봇을 피해 길을 짜지 못해 마당에서 몸이 닿고, 닿은 뒤 위치 추정이 틀어졌습니다(7.2절, 작업 기록 10.13절) |
| 어떻게 | 로봇마다 `pinky_peer_obstacles` 노드가 다른 로봇의 `/<로봇>/state`(10 Hz, map 자세)를 받아 몸을 덮는 원(반지름 0.08 m, 가운데는 바퀴 축에서 뒤로 0.018 m)을 점구름 `/<로봇>/peer_obstacles`로 냅니다. 두 costmap의 `peer_layer`(둘째 `ObstacleLayer`, `inflation_layer` 바로 앞)가 그것을 찍습니다 |
| 지나간 자리 | 같은 노드가 모든 빔이 `inf`인 한 바퀴 스캔 `/<로봇>/peer_sweep`을 냅니다. 층은 `inf_is_valid`로 그 빔을 따라 로봇 둘레 3 m를 매번 지운 뒤 지금 자리만 다시 찍습니다. 라이다 층과 따로인 층이라 라이다가 찍은 칸은 지우지 않습니다 |
| 켜고 끄는 법 | 로봇: `nav2.launch.py peer_obstacles:=true peer_robots:=pinky1,pinky2,pinky3`(기본 꺼짐). Gazebo: 기본 켜짐, 끄려면 `gz.launch.py peer_obstacles:=false`(노드는 `sim_stand_in` 프로세스 안에서 돕니다) |
| 자세의 출처 | 그 로봇의 위치 추정입니다. 추정이 틀어지면 찍는 자리도 틀립니다. 위치를 모르는 보고(`LOCALIZING`, 자세 0, 0, 0)는 쓰지 않고, 조용해진 로봇은 마지막 자리에 그대로 둡니다 |
| 다른 동작에 미치는 것 | `pinky_fsm`의 막힘 판단과 `BLOCKED`의 장애물 위치도 local costmap을 읽으므로 다른 로봇의 몸을 장애물로 봅니다. 고정 경로의 충돌 검사를 켜면(`fixed_line_collision_check:=true`) 고정 경로에서도 다른 로봇 앞에서 섭니다 |
| 남는 것 | 층은 가장 새 점구름 하나를 계속 씁니다. 노드가 죽으면 마지막 자리가 남습니다. 로봇에서 3 m보다 먼 칸은 지우지 않습니다(경기장은 그 안입니다) |
| 위치를 잃은 로봇 | 마지막으로 알던 자리에 장애물로 남습니다. 그 로봇이 실제로 다른 곳에 있으면 빈 자리를 막고 실제 자리는 막지 못합니다. "위치를 잃은 로봇은 서 있다"는 가정 위의 선택입니다. 지도 원점 (0, 0, 0) 그대로인 보고도 위치 모름으로 봅니다(원점은 경기장 모서리입니다) |

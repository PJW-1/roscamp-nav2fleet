# Pode 주행 계획서 (관제 맞춤, 2026-11-14)

이 문서는 로봇 주행 파트를 새 관제(ZoneTraffic, Nav2 goal 기반)에 맞추는 계획과 결과입니다. 브랜치는 `feat/pinky-drive`이고 `feat/layout-v7`(76ef0be)에서 시작했습니다.

사용자 지시(2026-11-14)는 셋입니다.

- 주행 파트를 관제에 맞게 계획하고 개발합니다.
- 회피는 임시로 구현하되 언제든 교체할 수 있게 합니다. 정밀 도킹은 건드리지 않습니다.
- 포트폴리오용이므로 안전보다 최고 성능에 비중을 둡니다.

## 1. 맡는 범위

| 구분 | 무엇 | 어디 |
|---|---|---|
| 맡는 것 | 관제 명령을 받아 움직이고 보고하는 상태 기계(MoveTo, Retreat, order 모델, 로봇단 교착 처리, 보고) | `pode/pode_fsm` |
| 맡는 것 | 고정 경로 주행과 Nav2 설정(FollowPath 셋, BT, costmap, goal checker, keepout, scan 거르기) | `pode/pode_nav_config` |
| 임시로 맡는 것 | 회피: 넓은 구역의 Nav2 goal을 모는 `FollowPathGoal` 값, 다른 로봇의 몸을 찍는 peer 층, 비전 관측원과 시뮬레이션의 비전 대역 | `pode/pode_avoidance`(4절) |
| 건드리지 않는 것 | 정밀 도킹. 시뮬레이션은 도크 대역(`sim_dock_stub:=true`)으로 대신합니다 | `pode/pode_dock` |
| 하지 않는 것 | 팀 레포 push, 실물 로봇 접속과 bringup, Confluence 수정 | |

## 2. 관제와 맞춘 경계

관제가 보내는 명령과 로봇이 하는 일은 `docs/Pode_계약.md`가 원본입니다. 주행 성능과 이어지는 부분만 모았습니다.

| 관제가 보내는 것 | 쓰는 곳(v7) | 로봇이 하는 일 | 성능에 걸리는 값 |
|---|---|---|---|
| `move_to` `follow_path` | 좁은 띠(급행, 갈림목, 도크 앞) | 받은 꺾은선을 FollowPath로 따릅니다. 꺾이는 곳은 반지름 0.10 m 호로 돕니다. 잠금 경계에서 끝나는 경로는 감속 없는 `FollowPathThrough`로 갑니다 | 속도 상한, 끝 감속 거리, 회전 속도 |
| `move_to` `nav_goal` | 넓은 구역(HALL, 대기 지점) | NavigateToPose를 보내고 길은 로봇의 Nav2가 짭니다. 컨트롤러는 `FollowPathGoal`(회피의 것)입니다 | `FollowPathGoal` 값, goal checker |
| 합친 `nav_goal` | 칸 입구(E-1~E-3, `through`)를 지나는 HALL 이음 | 중간 지점에 서지 않고 끝까지 goal 하나로 갑니다(관제가 합칩니다) | 같음 |
| order 모델(base, horizon) | 목적지 하나까지의 이동 | 조각 사이에서 서지 않고 이어 갑니다. 같은 방식이 이어지면 한 경로나 goal 바꾸기로 합칩니다 | 관제 `use_order_model`(2026-11-16부터 기본 켬) |
| `retreat` | 도크와 칸에서 물러나기 | `FollowPathReverse`로 0.05 m/s 후진합니다(0.10은 넣었다가 되돌림, 6.6). 끝 위치 허용치 0.02 m | 후진 속도 |
| `dock` | WORK, OUTBOUND | 정밀 도킹(범위 밖). 시뮬레이션은 대역이 3초 뒤 성공합니다 | |
| 보고 | 10 Hz `state` | `MOVING`, `RECOVERING`, `BLOCKED`, 앞 장애물 위치 | 도착 판정 0.15 m |

## 3. 성능을 재는 법

| 항목 | 내용 |
|---|---|
| 판 | `gz_v7_rush`(새로 만듦): v7 경기장, 세 대, 주문 12건이 처음 12초 안에 다 들어오고 고장과 장애물이 없습니다. 품목 수는 `gz_v7_varied`와 같습니다(1~4개) |
| 성능 | 마지막 주문이 출고될 때까지 걸린 시뮬레이션 시간(`summary.json`의 `duration_s`)과 분당 출고 수입니다. 팔이 품목마다 쓰는 4초와 도크 대역 3초는 주행과 상관없이 고정입니다 |
| 함께 보는 것 | 모든 주문 출고, 격리(`ISOLATED`)와 위반 0건, 로봇 사이 최소 거리(`fleet_check.json`의 `min_distance_m`), keepout 침범 깊이 |
| 값 바꾸기 | `gz.launch.py`의 새 인자 `nav_overrides:=<yaml>`로 Nav2 값을 파일 수정 없이 덮어 비교합니다. 충돌 검사와 속도 상한은 덮지 못합니다 |
| 견고함 | 고른 설정으로 `gz_v7_varied`(주문이 몰렸다 쉼, 배터리 부족 셋)와 장애물 `v7_yard_mix`를 한 판 돌려 회피가 깨지지 않는지 봅니다 |

## 4. 회피 교체 경계

회피는 회피 담당의 영역입니다(`docs/회피_약속.md`). 담당이 아직 넘기지 않아 임시 구현을 `pode_avoidance` 패키지 하나에 모았고, launch 인자 하나로 바꿀 수 있게 했습니다.

| 항목 | 내용 |
|---|---|
| 회피 패키지가 갖출 것 | `share/<패키지>/params/avoidance.yaml`(키 `follow_path_goal`, `vision_obstacles`, `peer_layer`만)과 `share/<패키지>/launch/avoidance.launch.py`(로봇 한 대의 회피 쪽 노드) |
| 고르는 법 | `nav2.launch.py`와 `gz.launch.py`의 `avoidance_package`(기본 `pode_avoidance`) |
| 임시 구현 | RPP `FollowPathGoal`(5절의 성능 값), peer 층(다른 로봇의 몸을 costmap에 찍음), 시뮬레이션 비전 대역(`/sim/obstacle_markers`의 상자를 카메라 시야 안에서 `/<robot>/vision_obstacles` 점으로 냄, 기본 꺼짐) |
| 교체하면 | 회피 담당이 같은 두 파일을 갖춘 패키지를 만들고 `avoidance_package:=<그 패키지>`로 띄웁니다. 관제와 `pode_fsm`은 바뀌지 않습니다 |

### 6.3 G2가 멈춘 까닭

- **일어난 일:** pode1이 S-001을 싣고 급행으로 W_X → O_X → O를 갔습니다. 로봇이 보고한 위치는 O(0.285, 0.90) 바로 옆 (0.307, 0.959)였지만, Gazebo 실제 위치를 재는 도크 대역은 x 오차 101 cm를 냈습니다. 실제 로봇은 x 1.30 근처에 있었고 위치 추정이 급행 방향으로 1 m 어긋났습니다.
- **원인(추정 포함):**
  1. 급행 띠는 폭이 0.18 m입니다(진열대 1의 북쪽 면 y 0.81, 북쪽 벽 y 0.99). 로봇 지름은 0.17 m입니다.
  2. G2의 로봇은 급행 직선에서 y 0.835~0.975로 흔들렸고 방향이 최대 41° 벗어났습니다. 이만큼 흔들리면 몸이 벽이나 진열대에 닿습니다.
  3. 로봇이 벽에 걸려 서 있는 동안 바퀴가 계속 돌아 오도메트리가 앞으로 나아간 것으로 셌다고 봅니다. 곧은 복도에서는 라이다가 앞뒤 방향의 차이를 보지 못해서 AMCL이 이 오차를 고치지 못합니다. 판 전체의 실제 위치 기록이 없어서 이 단계는 추정입니다.
- **흔들림의 까닭:** 이 세 판을 잴 때 고정 경로 컨트롤러(FollowPath, FollowPathThrough)의 앞보기는 0.10 m로 고정이었습니다(6.7에서 속도 비례로 바꿨습니다). 0.12 m/s에서는 0.83초 앞을 보지만 0.20 m/s에서는 0.5초 앞만 봅니다. 흔들림은 속도를 올린 G1에서 생겼고(1.1° → 10.3°), fast1의 빠른 제자리 회전(1.8 rad/s)이 더 키웠습니다(19.9°). 방향 오차가 0.70 rad(40°)를 넘으면 컨트롤러가 서서 도는데, G2는 41°까지 갔습니다.

### 6.5 앞보기 후보

앞보기를 속도에 비례하게 바꾸는 덮어쓰기입니다. 0.20 m/s 직선에서는 0.16 m(0.8초) 앞을 봐서 G0의 0.83초와 비슷합니다. 반지름 0.10 m 모퉁이 호에서는 곡률 규칙이 속도를 0.08 m/s로 낮춰 앞보기가 다시 0.10 m가 됩니다. 그러면 호 위의 앞보기 점은 지금처럼 0.52 rad 옆에 있어 서서 돌기(0.70 rad)를 부르지 않습니다.

```yaml
controller_server:
  ros__parameters:
    FollowPath:            # FollowPathThrough도 같은 네 값
      use_velocity_scaled_lookahead_dist: true
      lookahead_time: 0.8
      use_regulated_linear_velocity_scaling: true
      regulated_linear_scaling_min_radius: 0.25
```

`gz_v7_rush`를 `nav_max_speed:=0.20 use_order_model:=true nav_overrides:=<이 파일>`로 돌려 급행 흔들림이 G0 수준(표준편차 2° 안)으로 돌아오고 시간이 G1보다 늘지 않으면 기본값으로 넣고, 같은 설정으로 `gz_v7_varied`와 `v7_yard_mix` 견고함 판을 돌립니다. 이 판이 G3이고 결과는 6.7에 있습니다.

### 6.6 후진 0.10을 되돌린 까닭

후진을 0.10 m/s로 올리자(nav2, `pode_fsm`, 관제, 가짜 Pode를 함께) 가짜 로봇 시험 981개 가운데 7개가 실패했습니다. 브랜치가 시작한 76ef0be에서는 981개가 모두 통과합니다.

| 실패 | 내용 |
|---|---|
| 상황 `pose_jumps`, 배치 c, seed 1과 3(회피 흉내 perfect, none, mixed로 6개) | 20~40초 동안 pode1의 위치 보고가 옆으로 0.30 m 밀립니다. 후진이 빨라져 pode1이 그 창 안에서 갈림목 J_W를 지나게 됐고, 관제는 밀린 보고를 보고 J_W를 놓았습니다. 실제 로봇은 아직 J_W 안에 있었습니다(불변식 I3 위반) |
| order 꺼짐 골든 로그(fake_robots) | 후진 시간이 절반이 되어 사건 시각이 바뀝니다. 도킹 18번은 같고 두 상황이 10.6초와 16.2초 일찍 끝났습니다. 시각 차이뿐이라 다시 만들 수 있습니다 |

- **잠복 결함입니다:** 후진 0.05에서도 위치가 튀는 창의 시작을 14, 16, 18, 22, 24초로 옮기면 같은 I3 위반이 납니다. 관제의 `LOCALIZATION_SUSPECT`는 경고만 남기고(`pose_jump_m`, 기록만) 구역을 놓는 판단에는 쓰이지 않습니다. 기존 시험은 20초라는 시각 덕분에 통과하고 있었습니다.
- **xfail로 두지 않은 까닭:** `test_situation_avoid_modes.py`의 규칙은 주문을 못 끝낸 칸만 strict xfail로 두고, 불변식 위반은 숨기지 않고 실패하게 합니다.
- **다시 켜려면:** 사용자가 "튄 위치로는 구역을 놓지 않는다"(B7과 같은 위치 신뢰 정책)를 정하고 관제를 고친 뒤, 네 곳의 값을 0.10으로 바꾸고 fake_robots의 order 꺼짐 골든 로그를 다시 만듭니다.

### 6.7 속도 비례 앞보기와 기본 속도 0.20(2026-11-15)

6.5의 후보를 그대로 돌린 G3가 기준을 통과해서, 값을 기본 설정에 넣었습니다.

| 기준 | G1(앞보기 0.10 m 고정) | G3(속도 비례) |
|---|---|---|
| 급행 직선의 방향 흔들림(표준편차, 최대) | 10.3°, 33° | 1.6°, 6° |
| 급행 직선에서 지나간 y 범위(중심선 0.90) | 0.858~0.960 | 0.892~0.918 |
| 끝난 시각 | 343.1 s | 339.5 s |

- **넣은 값:** `nav2_params.yaml`의 고정 경로 컨트롤러 셋(`FollowPath`, `FollowPathThrough`, `FollowPathReverse`)에 `use_velocity_scaled_lookahead_dist: true`, `lookahead_time: 0.8`, `use_regulated_linear_velocity_scaling: true`, `regulated_linear_scaling_min_radius: 0.25`를 넣었습니다. 이 파일은 실물도 읽습니다.
- **속도별 앞보기:** 0.12 m/s에서는 전과 같은 0.10 m이고, 0.20 m/s에서는 0.16 m, 실물의 0.25 m/s에서는 0.20 m입니다. 후진(0.05 m/s)은 늘 0.10 m라서 전과 같습니다.
- **모퉁이:** 반지름 0.10 m 호에서는 곡률 규칙이 속도를 0.4배로 낮춰 앞보기가 0.10 m로 돌아옵니다. `test_nav_config.py`가 이 계산과 "호 위에서 서서 돌지 않는다"는 조건을 고정합니다.
- **Gazebo 기본 속도:** `nav_max_speed`의 기본값을 0.12에서 0.20으로 올렸습니다(`launch_parts.DEFAULT_SPEED_MPS`, `gz.launch.py`, `one_pode.launch.py`). 새 기본값만으로 돈 G4(order 꺼짐)는 356.5초로 G0보다 15.6% 빨랐고 흔들림은 1.4°였습니다.
- **관제의 속도 값:** 관제가 길 비용과 도착 예상에 쓰는 `nav_speed_mps`와 `follow_speed_mps`는 0.12 그대로입니다. Gazebo 속도를 따라가게 할지는 따로 재서 정합니다.

### 6.8 견고함 판과 그 판이 고친 것(2026-11-15)

견고함 판은 `gz_v7_varied`에 장애물 `v7_yard_mix`, `battery_low_pct:=20`, `use_order_model:=true`를 준 판입니다. 기준은 주문 12건을 모두 출고하고 격리가 없는 것입니다. 속도 0.12 m/s일 때의 같은 판은 600~999초였습니다.

| 판 | 설정 | 결과 | 일어난 일 |
|---|---|---|---|
| R1 | 0.20 기본값(6.7) | 실패 | pode1이 남쪽 진열대 동쪽 끝을 스치고 700초를 섰습니다. 넓은 구역 컨트롤러의 앞보기 1.5초가 0.20 m/s에서 상한 0.25 m에 닿아 모퉁이를 안쪽으로 잘랐습니다 |
| R2 | R1 + 넓은 구역 컨트롤러 값 | 통과, 748.2 s | 닿은 곳이 없습니다(방향 오차 1.1° 안). pode2가 P-3에 주차한 로봇 앞을 지나지 못해 115초를 섰습니다 |

| R4 | R3에서 회전만 1.0 rad/s로 되돌림 | 실패(도중에 멈춤) | 같은 자리에서 같은 일이 났습니다(방향 오차 47~96°). 회전 속도는 원인이 아니었습니다 |
| R5 | R4 + 칸막이 1, 2 위 끝의 계획 차단 | 통과, 575.2 s(R2보다 23% 빠름) | 위반 0건, 격리 0건, 로봇 사이 최소 거리 0.215 m, keepout 침범 0, 회복 시점에 잰 위치 추정 오차 최대 2.8 cm. 막힘 표시 1번 |

- **넓은 구역 컨트롤러 값(R1 → R2, G4 → G5):** `avoidance.yaml`의 `follow_path_goal`에서 앞보기를 1.5초에서 0.8초로(0.20 m/s에서 0.16 m) 줄이고, 굽이 감속을 켜고(`regulated_linear_scaling_min_radius` 0.25), goal 앞 감속 거리를 0.6 m에서 0.2 m로 줄였습니다. 급행 판은 356.5초에서 327.3초가 됐습니다.
- **고정 경로 끝 감속(G6 → G7):** v7의 고정 경로는 0.14~0.40 m라서 감속 거리 0.2 m가 구간의 절반을 덮었습니다. `FollowPath`와 `FollowPathReverse`의 `approach_velocity_scaling_dist`를 0.10 m로, 고정 경로 셋의 `min_approach_linear_velocity`를 0.08 m/s로 올렸습니다. 도킹 오차는 그대로였습니다(x 평균 2.9 cm, y 1.9 cm). 후진은 원하는 속도가 0.05 m/s라서 바닥 속도 0.08은 끝 감속을 없애는 효과만 있습니다.
- **제자리 회전 2.0 rad/s를 되돌린 까닭:** Gazebo의 구동 플러그인(`pode_sim.urdf.xacro`의 DiffDrive)은 `max_velocity` 1.0과 `max_acceleration` 2.0을 회전에도 겁니다. 2.0 rad/s로 명령한 판(G7, G8)과 1.0인 판(G6, G9)에서 로봇이 돈 속도는 같았습니다(중앙값 0.7, 90번째 백분위 1.0 rad/s). 빨라지지 않는 값을 남길 까닭이 없어 되돌렸고, `test_launch_wiring.py`가 어느 컨트롤러도 이 상한보다 빠른 회전을 명령하지 않는지 봅니다. 각가속도 3.2는 플러그인의 2.0보다 큰 채로 남아 있습니다(7절).
- **칸막이 1, 2 위 끝(R3, R4의 원인):** 칸을 나오는 고정 경로는 칸 입구(y 0.24)에 0.045 m 못 미친 y 0.195에서 끝난 것으로 처리되고, 로봇은 거기서 Q2로 가는 Nav2 goal을 받습니다. 5 cm 전역 costmap에서 y 0.15~0.20 줄은 칸막이 1과 2 위로 열려 있었습니다(`test_arena_v7.py`의 새 시험 8개가 고치기 전 지도에서 실패했습니다). 그래서 계획이 로봇의 출발 높이 그대로 동쪽으로 뻗었습니다. R2에서는 로봇이 y 0.19~0.20으로 지나가 3 cm가 남았지만, R3와 R4에서는 제자리에서 돈 뒤 y 0.165에서 출발해 실제 위치 y 0.154로 지나갔고 몸 옆(0.06)이 칸막이 끝(y 0.10)에 걸렸습니다. 칸막이 3에는 같은 까닭으로 넣은 차단(`keepout_extra`, y 0.20까지)이 이미 있었습니다. 같은 사각형을 칸막이 1(x 0.19~0.31)과 2(x 0.45~0.57)에 넣었습니다. 5 cm costmap은 칸 중심에서 마스크를 읽으므로 x 0.20~0.30과 0.45~0.55가 닫히고, 칸 가운데에서 0.05 m 안에 선 로봇의 출발 칸은 열려 있습니다(시험이 칸 셋, 치우침 다섯, 높이 넷을 봅니다). R5에서 같은 로봇이 y 0.21~0.22로 지나갔습니다.
- **R3와 R4에서 출발 높이가 낮아진 까닭:** 정하지 못했습니다. R2와 달라진 것은 고정 경로 끝 감속(칸을 더 빨리 나옵니다)과 6.9의 관제 변경입니다. 관제가 보낸 지시는 R2와 R4에서 같았습니다.
- **지도에서 바뀐 것:** `fleet_map_v7.yaml`의 `keepout_extra` 사각형 둘과 `arena_v7_keepout.pgm`입니다. 지점, 이음, 구역은 그대로입니다.
- **2026-11-17:** 남쪽 진열대 사이 건넘 틈을 막던 `keepout_extra` 사각형을 뺐습니다(사용자 결정: 지름길이라 막지 않고, 못 지나면 주행을 고칩니다). 칸막이 셋 둘레의 사각형은 그대로입니다([worklog_shelf_gap_open_2026-11-17.md](worklog_shelf_gap_open_2026-11-17.md)).

### 6.9 관제 쪽 개선(2026-11-15)

자세한 규칙은 `관제_구역교통.md`에 있습니다.

- 지점 기준 규칙은 다른 경우에 두는 0.05 m 여유를 이 경우에만 최대 전부 씁니다. O_OUT에서는 보고 위치가 구역 쪽으로 0.05 m 치우쳐도 몸과 구역 사이가 0.01 m입니다. 출고로 들어오는 로봇은 급행(y 0.90)으로 오고 떠나는 로봇은 y 0.66에 있으므로 두 로봇의 실제 거리는 0.24 m입니다.
- **이 변경들이 드러낸 관제 결함 하나를 고쳤습니다.** 관제 노드 통합 시험(진짜 노드와 가짜 로봇, 배치 d2)의 `order_burst`가 실패했습니다(10건 가운데 5건 출고, 격리). 출고 도크에서 N_E로 물러나던 로봇이 뒤로 지나가는 로봇 때문에 끝에서 0.2 m 앞(갈림목 안)에 섰는데, 잡음 섞인 보고 하나가 끝 지점에서 0.143 m로 보여 관제가 닿았다고 쳤고(`GOAL_ENDED_AT_TARGET`, 기준 0.15 m), 갈림목 안에서 받은 Nav2 goal이 세 번 실패했습니다. 이 판정은 전부터 있었고(이 작업 전 커밋에서도 한 번 났지만 그때는 통과했습니다), 대기 자리 전환과 지점 기준 놓기로 로봇들이 움직이는 박자가 바뀌면서 드러났습니다. 뒤가 막혀 선 후진은 선을 따라 남은 길이가 0.075 m를 넘으면 닿은 것으로 치지 않고, 뒤가 빌 때까지 기다렸다가 다시 물러나게 했습니다. 고친 뒤 `order_burst`는 10건을 305초에 출고했습니다(작업 전 309초). Gazebo 판(G0~G9, R1~R5)에서는 이 경로가 한 번도 쓰이지 않았으므로 위 표의 값은 그대로입니다.

## 9. 실물 지도 만들기와 시험 계획(2026-11-16)

2026-11-16 아침부터 학원에서 실물로 지도를 만들며 시험합니다. 이 절은 그때 볼 계획과 주의할 점입니다. 이 문서를 쓴 세션은 실물에 접속하지 않았고, 아래 순서와 통과 기준은 시뮬레이션과 코드에서 나온 제안입니다. 실물에서 확인한 것은 하나도 없습니다.

### 9.1 먼저 알아 둘 것

- **v7 배치는 실물로 놓아 본 적이 없는 가정입니다.** 지도는 벽 안쪽을 1.98 x 0.99 m로 잡았습니다. 2026-11-10에 라이다로 잰 값은 2.005 x 1.015 m이고 확인된 정확도가 없는 잠정값입니다(`docs/실측_2026-11-10.md`). 칸 빈 폭 0.24 m도 잠정값입니다(그림은 0.20).
- **좌표계가 맞아야 합니다.** 관제 지도(`fleet_map_v7.yaml`)의 원점은 남서쪽 벽 안쪽 모서리이고 x가 긴 변(동쪽), y가 짧은 변(북쪽)입니다. Nav2의 `map` 좌표가 이 좌표와 같아야 관제의 지점, 구역, keepout이 제자리에 놓입니다. 시뮬레이션은 지도를 관제 지도에서 그려 만들기 때문에 저절로 같았습니다.
- **Nav2는 지도 둘을 읽습니다.** costmap은 5 cm 지도(`map`), AMCL은 1 cm 지도(`map_fine`)를 읽고, `map_fine`을 주지 않으면 `map`을 씁니다. keepout 마스크(`keepout_mask`)는 따로 줍니다.
- **실물 설정이 시뮬레이션과 다른 곳:**

| 항목 | 실물 설정 | 시뮬레이션에서 잰 조건 | 주의 |
|---|---|---|---|
| 고정 경로 속도 | `desired_linear_vel` 0.25 m/s | 0.20 m/s까지 | 급행 폭 0.18 m를 0.25로 달리는 것은 재지 않았습니다 |
| 다른 로봇을 costmap에 찍는 층 | `peer_obstacles` 기본 false | true | v7은 로봇끼리 Nav2가 피하는 배치라 이 층을 켜야 합니다(지도 주석). 두 대부터는 `peer_obstacles:=true peer_robots:=...`를 줍니다 |
| 고정 경로 충돌 검사 | 켜짐 | 꺼짐 | 시뮬레이션에서 켰을 때 W(동쪽 벽에서 0.10 m)에 도킹하지 못하고 고립된 적이 있습니다. peer 층과 함께 켠 조합은 돌려 본 적이 없습니다 |
| 회전 | 각가속도 설정 3.2 rad/s^2 | Gazebo 구동이 1.0 rad/s, 2.0 rad/s^2에서 자름 | 실물의 회전 한계는 모릅니다 |
| 도킹 | 실제 도킹 | 도킹 흉내(`sim_dock_stub`) | 정밀 도킹은 손대지 않기로 했습니다. 오차만 기록합니다 |
| order 모델 | 기본 켬(2026-11-16) | 쇼는 켬 | 처음에는 `use_order_model:=false`로 끄고 시작합니다. 위치가 튀면 도크 구역을 놓는 문제(B7)가 켠 상태에서 더 직접 드러납니다 |

### 9.2 지도를 만드는 두 방법

| 방법 | 만드는 법 | 좋은 점 | 조건과 약점 |
|---|---|---|---|
| (가) 그린 지도 | `sim/fleet_gz_sim`에서 `PYTHONPATH=../../pc/fleet_core:. python3 -m fleet_gz_sim.arena --layout v7 --out <폴더>`. `maps/arena_v7.yaml`(5 cm), `arena_v7_fine.yaml`(1 cm), `arena_v7_keepout.yaml`이 나옵니다. 실물용은 `--real`을 붙입니다(시뮬 지도는 `sim_shelves`로 그리는데, 지금은 `shelves`와 같다). 실물용으로 만든 것은 `tools/real_pode/maps/`에 이미 있습니다 | 좌표계가 관제 지도와 저절로 같습니다. 1 cm 지도와 keepout도 함께 나옵니다 | 실제 경기장이 지도 치수와 1~2 cm 안으로 맞아야 AMCL이 맞습니다. 다르면 `fleet_map_v7.yaml`의 치수를 먼저 고쳐야 합니다. 지도에 없는 물체(팔 받침 등)는 들어가지 않습니다 |
| (나) SLAM 지도 | slam_toolbox로 만들고 저장합니다 | 실제 모양을 그대로 담습니다 | 원점과 방향을 관제 지도에 맞춰야 합니다. 벽과 나란하게 시작하고, 저장한 yaml의 `origin`을 남서쪽 안쪽 모서리가 (0, 0)이 되게 고칩니다. `origin`에 회전이 있으면 `tools/make_keepout.py`가 마스크를 만들지 않습니다. 11-10의 SLAM 지도는 2.5 cm였고 1 cm 지도는 따로 없습니다 |

| 4. 고정 경로(한 대) | 급행, 작업대 줄(Q2 → Q1 → W), 출고(O → O_OUT), 칸 출입 후진을 따로 달려 봅니다. 속도는 0.12에서 시작해 0.20, 0.25로 올립니다(설정 파일 복사본의 `desired_linear_vel`) | 선에서 벗어난 거리, 서는 거리, 도착 오차, 칸에 선 방향 | 급행에서 벽과 진열대에 닿지 않고, 끝에서 도착 허용 0.05 m 안에 섭니다 |
| 5. Nav2 goal(한 대) | 칸 입구에서 Q2, O_OUT에서 칸 입구로 가는 넓은 구역 goal을 보냅니다 | 걸린 시간, 서는 곳, "collision ahead" 경고 | keepout을 넘지 않고 도착합니다. O_OUT에서 출발할 때 서는지를 꼭 봅니다(8절) |
| 6. 도킹(한 대) | 작업대와 출고에 도킹합니다 | 관제 로그의 `DOCKED ... x, y, yaw` 오차 | 값만 기록합니다. 도킹을 마친 로봇이 구역을 놓는 규칙이 이 오차에 기대고 있습니다 |
| 7. 관제 한 대 | 관제를 붙여 주문 한 건을 끝까지 돌립니다(order 모델 끔) | 관제 로그, 걸린 시간 | 충전 칸 → 작업대 → 출고 → 칸으로 돌아옵니다 |
| 8. 두 대, 세 대 | peer 층을 켜고 두 대, 이어서 세 대로 주문 여러 건을 돌립니다. 그다음에 order 모델을 켭니다 | 최소 거리, BLOCKED 횟수, 격리 여부 | 접촉과 격리가 없습니다 |

### 9.4 꼭 재 올 값

시뮬레이션의 가정을 실물 값으로 바꾸는 데 필요한 것들입니다. 재 온 값이 있으면 지도와 설정을 그 값에 맞출 수 있습니다.

| 값 | 왜 필요한가 | 지금 가정 |
|---|---|---|
| 경기장 안쪽 치수, 진열대와 칸막이 자리, 칸 폭 | 지도 전체가 이 값 위에 있습니다 | 1.98 x 0.99 m, 칸 폭 0.24 m |
| AMCL 오차와 튀는 횟수 | 구역 놓기 여유 0.05 m와 튄 위치 결정의 근거 | 시뮬레이션에서 최대 3.4 cm |
| 직진 최고 속도에서 선을 벗어난 거리 | 기본 속도를 0.20으로 할지 0.25로 할지 | 0.20까지 잼 |
| 제자리 회전의 실제 속도와 미끄러짐 | 각가속도 3.2 설정이 실물에 맞는지 | Gazebo 상한 1.0 rad/s, 2.0 rad/s^2 |
| 끝에서 서는 거리와 도착 오차 | 끝 감속 0.10 m, 바닥 속도 0.08 m/s가 실물에 맞는지 | 재지 않음 |
| 도킹 오차(x, y, yaw) | 도킹 뒤 구역 놓기 규칙 | 재지 않음 |
| O_OUT에서 출발할 때 서는 시간 | 시뮬레이션의 26.6초가 실물에서도 나는지 | 원인 모름 |
| 칸에 선 방향 | 시뮬레이션에서는 73~112°로 삐뚤었습니다 | 90° |
| 라이다가 다른 Pode를 보는지 | 못 보면 로봇끼리 피하는 일을 peer 층에만 맡기게 됩니다 | 모름. Pode 높이 0.136 m, 라이다 면 0.125 m |
| 고정 경로 충돌 검사를 켠 채 W, O에 들어갈 수 있는지 | 실물 설정은 켜져 있습니다 | 시뮬레이션에서는 켜면 W에서 고립 |

### 9.5 주의할 점

- 값을 바꿀 때는 설정 파일의 복사본에서 바꾸고, 무엇을 얼마로 바꿨는지 적어 둡니다. 저장소의 값은 시험이 지키고 있어서 값만 바꾸면 시험이 실패합니다.
- 실측으로 `fleet_map_v7.yaml`을 고치면 지도와 keepout을 다시 만들어야 하고, `test_layout_v7.py`, `test_arena_v7.py`, 가짜 로봇의 기준 로그가 함께 바뀝니다. 치수만 재 오고 지도를 고치는 일은 시험과 함께 따로 하는 편이 안전합니다.
- 판을 돌릴 때는 rosbag으로 `amcl_pose`, `odom`, `cmd_vel`, `scan`과 관제 토픽을 남깁니다. 실물에서 생긴 일은 그 기록이 없으면 나중에 원인을 찾을 수 없습니다.
- 팀 레포 push와 Confluence 수정은 사용자가 정합니다.

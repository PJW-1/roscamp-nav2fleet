# 핑키 주행 계획서 (관제 맞춤, 2026-11-14)

이 문서는 로봇 주행 파트를 새 관제(ZoneTraffic, Nav2 goal 기반)에 맞추는 계획과 결과입니다. 브랜치는 `feat/pinky-drive`이고 `feat/layout-v7`(76ef0be)에서 시작했습니다.

사용자 지시(2026-11-14)는 셋입니다.

- 주행 파트를 관제에 맞게 계획하고 개발합니다.
- 회피는 임시로 구현하되 언제든 교체할 수 있게 합니다. 정밀 도킹은 건드리지 않습니다.
- 포트폴리오용이므로 안전보다 최고 성능에 비중을 둡니다.

## 1. 맡는 범위

| 구분 | 무엇 | 어디 |
|---|---|---|
| 맡는 것 | 관제 명령을 받아 움직이고 보고하는 상태 기계(MoveTo, Retreat, order 모델, 로봇단 교착 처리, 보고) | `pinky/pinky_fsm` |
| 맡는 것 | 고정 경로 주행과 Nav2 설정(FollowPath 셋, BT, costmap, goal checker, keepout, scan 거르기) | `pinky/pinky_nav_config` |
| 임시로 맡는 것 | 회피: 넓은 구역의 Nav2 goal을 모는 `FollowPathGoal` 값, 다른 로봇의 몸을 찍는 peer 층, 비전 관측원과 시뮬레이션의 비전 대역 | `pinky/pinky_avoidance`(4절) |
| 건드리지 않는 것 | 정밀 도킹. 시뮬레이션은 도크 대역(`sim_dock_stub:=true`)으로 대신합니다 | `pinky/pinky_dock` |
| 하지 않는 것 | 팀 레포 push, 실물 로봇 접속과 bringup, Confluence 수정 | |

## 2. 관제와 맞춘 경계

관제가 보내는 명령과 로봇이 하는 일은 `docs/핑키_계약.md`가 원본입니다. 주행 성능과 이어지는 부분만 모았습니다.

| 관제가 보내는 것 | 쓰는 곳(v7) | 로봇이 하는 일 | 성능에 걸리는 값 |
|---|---|---|---|
| `move_to` `follow_path` | 좁은 띠(급행, 갈림목, 도크 앞) | 받은 꺾은선을 FollowPath로 따릅니다. 꺾이는 곳은 반지름 0.10 m 호로 돕니다. 잠금 경계에서 끝나는 경로는 감속 없는 `FollowPathThrough`로 갑니다 | 속도 상한, 끝 감속 거리, 회전 속도 |
| `move_to` `nav_goal` | 넓은 구역(HALL, 대기 지점) | NavigateToPose를 보내고 길은 로봇의 Nav2가 짭니다. 컨트롤러는 `FollowPathGoal`(회피의 것)입니다 | `FollowPathGoal` 값, goal checker |
| 합친 `nav_goal` | 칸 입구(E-1~E-3, `through`)를 지나는 HALL 이음 | 중간 지점에 서지 않고 끝까지 goal 하나로 갑니다(관제가 합칩니다) | 같음 |
| order 모델(base, horizon) | 목적지 하나까지의 이동 | 조각 사이에서 서지 않고 이어 갑니다. 같은 방식이 이어지면 한 경로나 goal 바꾸기로 합칩니다 | 관제 `use_order_model`(기본 꺼짐) |
| `retreat` | 도크와 칸에서 물러나기 | `FollowPathReverse`로 0.05 m/s 후진합니다(0.10은 넣었다가 되돌림, 6.6). 끝 위치 허용치 0.02 m | 후진 속도 |
| `dock` | WORK, OUTBOUND | 정밀 도킹(범위 밖). 시뮬레이션은 대역이 3초 뒤 성공합니다 | |
| 보고 | 10 Hz `state` | `MOVING`, `RECOVERING`, `BLOCKED`, 앞 장애물 위치 | 도착 판정 0.15 m |

## 3. 성능을 재는 법

| 항목 | 내용 |
|---|---|
| 판 | `gz_v7_rush`(새로 만듦): v7 경기장, 세 대, 주문 12건이 처음 12초 안에 다 들어오고 고장과 장애물이 없습니다. 품목 수는 `gz_v7_varied`와 같습니다(1~4개) |
| 성능 | 마지막 주문이 출고될 때까지 걸린 시뮬레이션 시간(`summary.json`의 `duration_s`)과 분당 출고 수입니다. 팔이 품목마다 쓰는 4초와 도크 대역 3초는 주행과 상관없이 고정입니다 |
| 함께 보는 것 | 모든 주문 출고, 격리(`ISOLATED`)와 위반 0건, 로봇 사이 최소 거리(`fleet_check.json`의 `min_distance_m`), keepout 침범 깊이 |
| 값 바꾸기 | `gz.launch.py`의 새 인자 `nav_overrides:=<yaml>`로 Nav2 값을 파일 수정 없이 덮어 비교합니다. 충돌 검사와 속도 상한은 덮지 못합니다 |
| 견고함 | 고른 설정으로 `gz_v7_varied`(주문이 몰렸다 쉼, 배터리 부족 셋)와 장애물 `v7_yard_mix`를 한 판 돌려 회피가 깨지지 않는지 봅니다 |

## 4. 회피 교체 경계

회피는 회피 담당의 영역입니다(`docs/회피_약속.md`). 담당이 아직 넘기지 않아 임시 구현을 `pinky_avoidance` 패키지 하나에 모았고, launch 인자 하나로 바꿀 수 있게 했습니다.

| 항목 | 내용 |
|---|---|
| 회피 패키지가 갖출 것 | `share/<패키지>/params/avoidance.yaml`(키 `follow_path_goal`, `vision_obstacles`, `peer_layer`만)과 `share/<패키지>/launch/avoidance.launch.py`(로봇 한 대의 회피 쪽 노드) |
| 고르는 법 | `nav2.launch.py`와 `gz.launch.py`의 `avoidance_package`(기본 `pinky_avoidance`) |
| 임시 구현 | RPP `FollowPathGoal`(5절의 성능 값), peer 층(다른 로봇의 몸을 costmap에 찍음), 시뮬레이션 비전 대역(`/sim/obstacle_markers`의 상자를 카메라 시야 안에서 `/<robot>/vision_obstacles` 점으로 냄, 기본 꺼짐) |
| 교체하면 | 회피 담당이 같은 두 파일을 갖춘 패키지를 만들고 `avoidance_package:=<그 패키지>`로 띄웁니다. 관제와 `pinky_fsm`은 바뀌지 않습니다 |

## 6. 결과

### 6.1 측정(`gz_v7_rush`, 2026-11-14)

세 판 모두 후진 0.05 m/s(지금 기본값)로 쟀습니다.

| 판 | 설정 | 끝난 시각 | 마지막 출고 | 분당 출고 | 주문 | 로봇 사이 최소 거리 | 급행 직선의 방향 흔들림(표준편차, 최대) |
|---|---|---|---|---|---|---|---|
| G0 | 기본값(속도 0.12, order 꺼짐) | 422.6 s | 391.5 s | 1.84 | 12건 모두 출고 | 0.235 m | 1.1°, 4° |
| G1 | 속도 0.20, order 켬, 회전 규칙 | 343.1 s(18.8% 빠름) | 320.4 s | 2.25 | 12건 모두 출고 | 0.206 m | 10.3°, 33° |
| G2 | G1 + fast1(회전 1.8 rad/s, goal 끝 감속 거리 0.2 m) | 끝나지 않음 | | | S-001이 출고 도킹에 세 번 실패 | | 19.9°, 41° |

- 두 판(G0, G1)은 위반과 격리가 0건이고 keepout 침범 깊이도 0입니다. 위치 추정(AMCL)과 Gazebo 실제 위치의 차이는 회복 시점에 잰 값으로 최대 3.4 cm였습니다.
- 흔들림은 급행 직선(x 0.75~1.45, y 0.8~1.0)을 MOVING으로 지나는 모든 보고에서 방향이 서쪽(180°)에서 벗어난 각도입니다.

### 6.2 시간이 간 곳

| 판 | MOVING 시간(세 대 합) | 나눈 것 | 기다림 |
|---|---|---|---|
| G0 | 742 s | 정상 주행 443 s, 제자리 회전 104 s, 느린 직진 195 s | 43번(제자리 회전 때문 20번, BLOCKED 6번) |
| G1 | 따로 재지 않음 | 평균 속도 0.098 m/s. 제자리 회전 99 s(O_OUT 48 s), 느린 직진 144 s(O_X 36, Q2 29, E-1 20, O_OUT 19, E-2 15 s) | 13번(제자리 회전 때문 6번, BLOCKED 2번은 (0.16, 0.27) 부근) |

G1은 속도, order 모델, 회전 규칙을 한꺼번에 바꿨으므로 기다림이 줄어든 몫을 하나씩 나누지는 못합니다.

### 6.3 G2가 멈춘 까닭

- **일어난 일:** pinky1이 S-001을 싣고 급행으로 W_X → O_X → O를 갔습니다. 로봇이 보고한 위치는 O(0.285, 0.90) 바로 옆 (0.307, 0.959)였지만, Gazebo 실제 위치를 재는 도크 대역은 x 오차 101 cm를 냈습니다. 실제 로봇은 x 1.30 근처에 있었고 위치 추정이 급행 방향으로 1 m 어긋났습니다.
- **원인(추정 포함):**
  1. 급행 띠는 폭이 0.18 m입니다(진열대 1의 북쪽 면 y 0.81, 북쪽 벽 y 0.99). 로봇 지름은 0.17 m입니다.
  2. G2의 로봇은 급행 직선에서 y 0.835~0.975로 흔들렸고 방향이 최대 41° 벗어났습니다. 이만큼 흔들리면 몸이 벽이나 진열대에 닿습니다.
  3. 로봇이 벽에 걸려 서 있는 동안 바퀴가 계속 돌아 오도메트리가 앞으로 나아간 것으로 셌다고 봅니다. 곧은 복도에서는 라이다가 앞뒤 방향의 차이를 보지 못해서 AMCL이 이 오차를 고치지 못합니다. 판 전체의 실제 위치 기록이 없어서 이 단계는 추정입니다.
- **흔들림의 까닭:** 고정 경로 컨트롤러(FollowPath, FollowPathThrough)는 앞보기가 0.10 m로 고정입니다. 0.12 m/s에서는 0.83초 앞을 보지만 0.20 m/s에서는 0.5초 앞만 봅니다. 흔들림은 속도를 올린 G1에서 생겼고(1.1° → 10.3°), fast1의 빠른 제자리 회전(1.8 rad/s)이 더 키웠습니다(19.9°). 방향 오차가 0.70 rad(40°)를 넘으면 컨트롤러가 서서 도는데, G2는 41°까지 갔습니다.

### 6.4 결정

| 항목 | 결정 | 까닭 |
|---|---|---|
| fast1 | 넣지 않음 | G2가 멈췄습니다 |
| Gazebo 기본 속도 0.20과 order 모델 | 넣지 않음. 기본값 0.12와 order 꺼짐을 그대로 둡니다 | G1은 18.8% 빨랐지만 급행에서 벽에 닿을 만큼 흔들렸습니다. 한 판의 성공으로는 믿기 어렵습니다. 6.5의 앞보기 후보로 다시 잰 뒤 정합니다. 데모는 `nav_max_speed:=0.20 use_order_model:=true`로 G1 설정을 그대로 띄울 수 있습니다 |
| 제자리 회전 규칙 | 넣음 | 마지막 직진 뒤 4초(`nav_turn_window_s`) 안에서 쌓인 회전이 0.2 rad(`nav_turn_progress_rad`)를 넘을 때마다 현장 양보의 시작만 미룹니다. BLOCKED 시계는 몸 중심의 이동으로만 잽니다. 그래서 RECOVERING은 5초 안, 관제 `stall_s` 12초 전입니다 |
| `nav_turn_window_s` 6초 | 4초로 둠 | 6초여도 계약 안(RECOVERING 7초, BLOCKED 9초)이지만, G1의 BLOCKED 2번이 회전 때문이라는 근거가 없습니다 |
| 후진 0.10 m/s | 되돌림(기준값 0.05) | 6.6. 네 곳(nav2 `FollowPathReverse`, `pinky_fsm` `reverse_speed_mps`, 관제 `retreat_speed_mps`, 가짜 핑키의 상한)이 같은 값인지 견주는 시험은 남겼습니다 |

| 회피 패키지 | 넣음 | 4절 |

### 6.5 다음 후보(실행 전)

앞보기를 속도에 비례하게 바꾸는 덮어쓰기입니다. 0.20 m/s 직선에서는 0.16 m(0.8초) 앞을 봐서 G0의 0.83초와 비슷합니다. 반지름 0.10 m 모퉁이 호에서는 곡률 규칙이 속도를 0.08 m/s로 낮춰 앞보기가 다시 0.10 m가 됩니다. 그러면 호 위의 앞보기 점은 지금처럼 0.52 rad 옆에 있어 서서 돌기(0.70 rad)를 부르지 않습니다.

```yaml
controller_server:
  ros__parameters:
    FollowPath:            # FollowPathThrough도 같은 네 값
      use_velocity_scaled_lookahead_dist: true
      lookahead_time: 0.8
      use_regulated_linear_velocity_scaling: true
      regulated_linear_scaling_min_radius: 0.25
```

`gz_v7_rush`를 `nav_max_speed:=0.20 use_order_model:=true nav_overrides:=<이 파일>`로 돌려 급행 흔들림이 G0 수준(표준편차 2° 안)으로 돌아오고 시간이 G1보다 늘지 않으면 기본값으로 넣고, 같은 설정으로 `gz_v7_varied`와 `v7_yard_mix` 견고함 판을 돌립니다.

### 6.6 후진 0.10을 되돌린 까닭

후진을 0.10 m/s로 올리자(nav2, `pinky_fsm`, 관제, 가짜 핑키를 함께) 가짜 로봇 시험 981개 가운데 7개가 실패했습니다. 브랜치가 시작한 76ef0be에서는 981개가 모두 통과합니다.

| 실패 | 내용 |
|---|---|
| 상황 `pose_jumps`, 배치 c, seed 1과 3(회피 흉내 perfect, none, mixed로 6개) | 20~40초 동안 pinky1의 위치 보고가 옆으로 0.30 m 밀립니다. 후진이 빨라져 pinky1이 그 창 안에서 갈림목 J_W를 지나게 됐고, 관제는 밀린 보고를 보고 J_W를 놓았습니다. 실제 로봇은 아직 J_W 안에 있었습니다(불변식 I3 위반) |
| order 꺼짐 골든 로그(fake_robots) | 후진 시간이 절반이 되어 사건 시각이 바뀝니다. 도킹 18번은 같고 두 상황이 10.6초와 16.2초 일찍 끝났습니다. 시각 차이뿐이라 다시 만들 수 있습니다 |

- **잠복 결함입니다:** 후진 0.05에서도 위치가 튀는 창의 시작을 14, 16, 18, 22, 24초로 옮기면 같은 I3 위반이 납니다. 관제의 `LOCALIZATION_SUSPECT`는 경고만 남기고(`pose_jump_m`, 기록만) 구역을 놓는 판단에는 쓰이지 않습니다. 기존 시험은 20초라는 시각 덕분에 통과하고 있었습니다.
- **xfail로 두지 않은 까닭:** `test_situation_avoid_modes.py`의 규칙은 주문을 못 끝낸 칸만 strict xfail로 두고, 불변식 위반은 숨기지 않고 실패하게 합니다.
- **다시 켜려면:** 사용자가 "튄 위치로는 구역을 놓지 않는다"(B7과 같은 위치 신뢰 정책)를 정하고 관제를 고친 뒤, 네 곳의 값을 0.10으로 바꾸고 fake_robots의 order 꺼짐 골든 로그를 다시 만듭니다.

# 관제 노드 IR-30 구조: 코어 그룹과 받은 편지함 (2026-11-25)

- 브랜치: `feat/fleet-inbox-2026-11-25` (origin/main `c29de003`에서 땀). main 병합은 사용자가 말할 때만 한다.
- 설계 검토 사항 Q-23을 이 구조로 결정했다(팀 PR #15에 같은 변경을 넣음).
- 목표: IR-30(`call_async`, 응답 콜백은 다른 콜백 그룹, `MultiThreadedExecutor`)을 지키면서 코어 상태는 한 곳에서만 바꾼다. `fleet_core`는 바꾸지 않았다.

## 1. 바뀐 것

| 무엇 | 전 | 후 |
|---|---|---|
| 실행기 | `rclpy.spin` (단일 스레드) | `make_executor()` = `MultiThreadedExecutor(num_threads=4)` |
| 코어 그룹 | 없음 (기본 그룹 하나) | `MutuallyExclusiveCallbackGroup` 하나: 틱, heartbeat, `/fleet/robots` 발행, 서버 `confirm_clear` · `reinstate` · `force_ship` |
| 받은 편지함 그룹 | 없음 | 구독(`robot_state` · `arm_state` · `order_board` · `system_mode`), 액션 goal 수락 · feedback · 결과, 서비스 응답(`check_clear` · `report_order` · `set_mode`) |
| 받은 편지함 콜백이 하는 일 | 코어를 바로 고침 | `Inbox`(스레드 안전한 큐)에 처리 함수와 인자만 넣음 |
| 큐 비우기 | 해당 없음 | 틱 시작과 서버 콜백 시작에서 비우고, 넣은 순서대로 처리 |

- **future 완료 콜백도 넣기만 한다.** rclpy는 future 완료 콜백을 실행기 작업으로 돌리므로 콜백 그룹의 제약을 받지 않는다. 그래서 `_mode_answered` · `_report_answered` · `_clear_answered` · `_goal_response` · `_goal_result`와 feedback은 모두 `partial(self._post, 처리 함수, ...)`로 등록했다.
- **기록과 재생 순서:** 처리 함수 이름과 본문은 그대로다. 큐에서 꺼낸 순서대로 처리 함수가 코어를 부르므로, 코어 입력 기록(`--record`) 순서가 곧 꺼낸 순서다.
- **heartbeat는 코어 그룹에 둔다.** 코어가 멈추면 heartbeat도 끊겨 로봇이 IR-34대로 서야 하기 때문이다(코드에 한 줄 주석).
- **기다리는 호출 없음:** 동기 `call()`, `spin_until_future_complete`, `spin_once`를 쓰지 않는다. 정적 시험으로 막는다.
- **틱 처리 시간:** 큐 비우기를 포함한 틱이 주기(`1 / tick_hz`)를 넘으면 5초에 한 번까지 경고 로그를 낸다. 로그에는 그 틱에서 기다린 사건 수와 큐 최대 길이(`Inbox.peak`)가 들어간다.
- **확인용 표시:** 코어 그룹 콜백은 `_core_callback` 장식자로 감싸 그 콜백이 도는 스레드를 `_core_thread`에 남긴다. 시험이 "코어는 코어 그룹 안에서만 불렸다"를 확인할 때 쓴다.
- 문서: `pc/fleet_manager/README.md`에 동시성 구조 절을 새로 썼다.

파일: `fleet_manager/inbox.py`(새 파일), `fleet_manager/fleet_manager_node.py`, `pc/fleet_manager/README.md`, `package.xml`(`std_srvs` 시험 의존).

## 2. 시험

새 시험은 구현 전에 먼저 썼다.

| 파일 | 개수 | 확인하는 것 |
|---|---|---|
| `test_inbox.py` | 3 | 넣은 순서대로 나온다, `peak`, 여러 스레드가 동시에 넣어도 빠지는 것이 없다 |
| `test_node_inbox.py` | 5 | 콜백마다 그룹이 맞다. 받은 편지함 콜백은 큐에 넣기만 하고 틱이 코어에 넘긴다. 꺼낸 순서대로 기록되고 재생하면 같다. 실제 그래프에서 코어 호출이 모두 코어 그룹 안에서 일어난다. 느린 틱 경고는 5초에 한 번까지 |
| `test_executor_deadlock.py` | 3 | 작은 노드로 교착 재현: (a) 단일 스레드에서 콜백 안에서 응답을 기다리면 제한 시간(2 s)까지 끝나지 않는다, (b) `call_async`와 완료 콜백은 단일 스레드에서도 응답을 받는다, (c) 다중 스레드와 다른 콜백 그룹이면 같은 대기도 제한 시간 안에 끝난다 |
| `test_no_blocking_calls.py` | 2 | AST로 패키지 안에 `.call(` · `spin_until_future_complete` · `spin_once`가 없다. 검사기가 실제로 잡는지 작은 예제로 보인다 |

**고친 기존 시험:** 기대값을 바꾼 시험은 없다. 새 구조에 맞춰 시험을 돌리는 방법만 고쳤다.
- `test_node_wiring.py`의 기록 · 재생 시험은 기대값은 그대로 두고, 노드를 `main()`과 같은 실행기(`make_executor()`)로 돌리게만 바꿨다. 단일 스레드로 돌리면 새 구조를 시험하지 않기 때문이다.
- `test_node_order.py`의 feedback 시험 둘은 콜백을 직접 부른 뒤 `node._drain()`을 한 번 부르고 확인한다. 이제 콜백은 큐에 넣기만 하기 때문이다. 하나에는 "큐를 비우기 전에는 코어가 불리지 않는다"는 확인을 더했다.
- `test_node_wiring.py`의 보고 재전송 시험 넷이 쓰는 가짜 노드 객체에 `_post`(바로 처리)를 더했다. 완료 콜백이 `_post`를 거치기 때문이다.
- 팀 레포에서는 가짜 노드 객체를 쓰는 시험 둘(`test_order_report_adapters.py`, `test_report_flush.py`)의 가짜 객체에 `_core_group` · `_inbox_group` · `_post` · `_drain`을 더했다. 기대값은 바꾸지 않았다.

- **큐 최대 길이:** 3대 8~10, 10대 14~18, 20대 26~29.

## 4. Codex 검토

범위 `c29de003..HEAD`(측정 도구 제외)를 한 번 검토했다. 지적 넷을 코드에서 확인했고, 넷 다 전보다 나빠진 결함이 아니라고 판단해 코드는 고치지 않았다.

| 지적 | 판단 |
|---|---|
| 큐에 수신 시각이 없어, 오래 기다린 상태가 막 받은 상태로 처리된다 | 처리 시각은 꺼낸 시각이고 정상일 때 한 틱(100 ms) 안이다. 전에도 실행기가 바쁘면 메시지가 rmw 큐에서 기다렸다가 처리 시각으로 찍혔다. 정상일 때 처리 시각은 받은 시각보다 최대 한 틱(100 ms) 늦고, 통신 끊김 판정 시간(초 단위)에 비해 작아 그대로 둔다. 코어가 판단에 쓰는 것은 둘 다 다음 틱이다 |
| 큐 길이 제한이 없어 과부하에서 메모리가 늘고 heartbeat가 늦어진다 | 아래 "남은 것"에 적었다. 코어가 밀리면 heartbeat가 늦어지는 것은 일부러 둔 것이다(IR-34). 결과 사건은 버리면 안 되므로 버리는 상한은 두지 않았다 |
| 종료할 때 큐에 남은 사건을 처리하지 않고 버린다 | 전에도 Ctrl-C로 멈추면 rmw 큐에 남은 콜백은 처리되지 않았다. 종료 중에 큐를 비우면 새 goal을 보낼 수 있어 그대로 둔다 |
| 보고 응답 시험은 가짜 `_post`로 바로 처리해 큐 경로를 거치지 않는다 | 그 시험이 원래 보던 응답 · 만료 처리 논리는 그대로 확인한다. 큐에 넣고 틱에서 넘기는 경로는 `test_node_inbox.py`가 실제 노드로 확인한다 |

## 5. 남은 것

- **main 병합과 nav2fleet 동기화:** 사용자가 말할 때 한다. 실물에서는 아직 돌려 보지 않았다.
- **큐 길이 제한 없음:** `Inbox`는 길이 제한이 없다. 코어가 멈추면 큐가 계속 길어지지만, 그때는 heartbeat도 끊겨 로봇이 선다(IR-34).
- **측정 도구의 한계:** 측정 도구의 Codex 지적 넷 중 둘(예외가 나도 가짜 로봇을 정리, 일부 로봇만 보고하면 경고)은 고쳤다(`d0d25626`). 나머지 둘은 남았다. 측정 구간은 1초 단위로 끝나서 지정한 90초보다 조금 길 수 있다. 주문은 가짜 central의 시나리오 시계로 나가므로, 로봇 준비 시간이 다르면 측정 시작 때의 주문 진행이 조금씩 다르다.
- **20대 규모의 틱 비용:** 20대에서 틱이 p50 기준 40~50 % 길고, 부하가 높을 때 주기를 넘는 틱이 생긴다. 대수를 늘리기 전에 큐 처리 몫과 실행기 스레드 경쟁 몫을 나눠 재고, 스레드 수(지금 4)를 줄이는 것과 비교한다.
- **운영 모드 맞추기(같은 날 set_mode 작업):** 모드가 다른 Pode가 제외 시각(두 번째 호출 + 2 s)보다 짧은 간격으로 계속 재부팅하면 끝내 제외되지 않는다. 재부팅에는 프로그램 시작과 DDS 연결 시간이 들어 4초 안쪽으로 되풀이되기는 어렵다고 보고 그대로 두었다.
